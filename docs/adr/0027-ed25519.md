# 0027. Ed25519 is the signature algorithm

**Status:** Accepted
**Date:** 2026-10-17

## Context

Every trust relation in LP is a signature: a master key over a self-signing key, a
self-signing key over a binding or principal with a role, a user-signing key over a known
person, a group key over a membership document, a device key over a revocation or relay
list (chapters 01, 02, 06, 10). One algorithm keeps verification code, test vectors and key
rendering simple; the multicodec prefix on rendered keys (ADR 0020) means a second
algorithm could be added later without a format change.

## Decision

**Ed25519** (RFC 8032) is the only signature algorithm for master, self-signing,
user-signing, group, principal and binding keys. Public keys render as multibase base58btc
with the multicodec `ed25519-pub` prefix, so an Ed25519 key always begins `z6Mk`.
Signatures are the 64-byte Ed25519 signature over the fact's bytes as transmitted, with a
domain prefix and type (ADR 0035). The same device key is presented as the TLS raw public key
(RFC 7250) on QUIC connections, so TLS 1.3 negotiation must offer `ed25519` as a signature
scheme.

## Consequences

Small keys and signatures, fast verification on phones and hubs, wide library support
(`ed25519-dalek` in Rust, and every platform keystore except where hardware-backed keys
are limited to ECDSA P-256, which is noted as a platform constraint in chapter 08 rather
than a reason to change the default). No algorithm negotiation anywhere in the protocol
for now. Adding a post-quantum or hardware-constrained alternative later is a new ADR and
a new multicodec prefix, not a redesign.
